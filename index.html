QQ流量分析(PC-PC端、PC-手机端)

说明：本文的实验数据来自一次“手机端 → PC 端”的 QQ 图片传输抓包。PC-PC 端的分析流程与本文相同，文末给出复现方法；没有实际捕获到的数据不写入结论。实验只涉及本人设备和本人账号，截图中的账户、昵称、历史文件名、分享链接、URL token 以及包详情中的 MAC 地址已做裁剪或遮挡，原始 pcap 不公开。

一、作业要求

这次作业要求围绕三个问题展开：

  1. UDP 还是 TCP：QQ 的流量跑在哪种传输层协议上？
  2. 加密还是明文：传输内容是否可读？
  3. 恢复可能为明文传输的文件：如果文件是明文传输，能否还原？

同时要求使用 Wireshark 捕获、识别并分析相关流量，发布到博客，并注意保护个人隐私。

三、问题一：UDP 还是 TCP

过滤手机端 IP 后，抓包结果如下：

使用的显示过滤器：

本次抓包共 15103 个分组，过滤后显示 1669 个。从截图中可以观察到：

  • 协议列全部是 TCP，没有看到 UDP 参与这次照片传输；
  • 源端口为 8082，目的端口为 63151；
  • 第一条记录是 8082 → 63151 [SYN, ACK]，说明 PC 主动连接手机端的 8082 端口，手机端临时充当服务器，PC 作为客户端；
  • 分组列表底部还可以看到一条 HTTP 协议记录（No. 14652），说明应用层是 HTTP。

因此，本次手机端 → PC 端的照片传输使用的是 TCP，应用层为 HTTP。TCP 负责可靠传输，适合 2.19 MB 这种需要完整到达的文件；HTTP 则负责把文件封装成请求和响应。

需要说明的是：这个结论只针对本次抓到的照片传输。QQ 的其他功能（例如心跳、语音、视频）可能使用 UDP，本文没有捕获到，因此不作断言。

四、问题二：加密还是明文

4.1 第一眼：像加密

选中一个承载文件数据的 TCP 包（No. 12925），在 Wireshark 的十六进制视图里，载荷是大量不可打印字节，单包 TCP 载荷长度为 1380 字节：

（十六进制视图中的载荷呈高熵，乍看很像密文）

如果只看十六进制，很容易误判为“加密流量”。但“看起来像乱码”不能作为加密的依据——JPEG、压缩包等二进制文件本身就不是可打印文本。

4.2 跟踪 TCP 流：看到明文 HTTP 头

对这条 TCP 流执行 分析 → 追踪 → TCP 流（过滤器 tcp.stream eq 54），把“显示为”切换成 ASCII，可以看到完整的 HTTP 请求和响应头：

（HTTP 头为明文；URL token 和包详情中的 MAC 地址文本已打码）

截图中的关键信息如下（URL 中的 token 已打码）：

可以看到：

  • 请求行、Host、User-Agent、Server: QQ/1.0.0 (Tencent)、Content-Length 等都是 明文；
  • Content-Length: 2295406 字节约为 2.19 MB，与手机端显示的照片大小一致；
  • 服务器标识是 QQ/1.0.0 (Tencent)，说明这是 QQ 自己实现的 HTTP 服务，而不是普通的 Web 服务器；
  • Host 是手机端的 10.34.7.110:8082，进一步印证了“手机端起临时 HTTP 服务、PC 端下载”的判断。

换句话说，操作上看起来是“手机端发送照片”，但在协议层面，实际是 PC 端向手机端的临时 HTTP 服务发起 GET 请求并下载文件。

4.3 响应体：JPEG 的 EXIF 也是明文

HTTP 头之后是响应体。在 ASCII 视图中可以直接看到：

这些是 JPEG 的 EXIF 元数据，包含相机型号、固件版本、拍摄时间等信息。如果响应体被加密，这些字符串不可能以明文出现。因此可以判断：不仅 HTTP 头是明文，照片文件本身也是明文传输的。

结论：

  • 传输层：TCP；
  • 应用层：HTTP；
  • 内容：HTTP 头明文，JPEG/EXIF 明文；
  • 这不是“加密流量”，而是一次 明文文件传输。

五、问题三：恢复明文文件

既然文件是明文 JPEG，就可以直接从 TCP 流中还原。

5.1 方法一：导出 HTTP 对象

如果 Wireshark 把该端口识别为 HTTP，可以直接使用：

5.2 方法二：跟踪 TCP 流并保存原始数据

  3. 点击“另存为…”，保存为 .bin；
  4. 用 binwalk、foremost 或按文件头手工截取。

5.5 为什么这次能恢复

  • 文件没有加密；
  • HTTP 响应头给出了准确的长度；
  • JPEG 有固定的文件头 FF D8 FF 和文件尾 FF D9，便于定位和截取；
  • 传输过程没有经过 TLS，因此不需要任何密钥。

这也是题目提示里“不同文件有不同的头部，可以作为文件开始的特征码”和“在线传输方式”的具体体现：先识别文件类型，再按 HTTP 对象或 TCP 流导出。

六、PC-PC 端怎么复现

本文的实验数据来自手机端 → PC 端。PC-PC 端的分析步骤完全一样，建议按下面的流程补做：

  1. 两台 PC 登录两个 QQ，连接同一局域网；
  2. 在接收端启动 Wireshark；
  3. 发送一条唯一文本（如 MARKER-20261025）、一张图片、一个压缩包；
  4. 先看 统计 → 会话，找到 QQ 的 TCP/UDP 流；
  5. 对可疑流执行 追踪 → TCP 流，判断是 HTTP 明文还是 TLS 加密；
  6. 如果是明文 HTTP，用 导出对象 → HTTP 恢复文件；如果是 TLS，记录 SNI、端口和包长，说明无法直接解密。

预期上：

  • 如果两台 PC 在同一局域网且 QQ 走直连，可能会看到类似本文的 HTTP 明文传输；
  • 如果走服务器中转，可能是 TLS 加密流量，能否恢复要以实际抓包为准。

为避免编造数据，本文不写未捕获到的 PC-PC 结论。

七、隐私保护

这次实验只涉及本人设备、本人账号和本人发送的照片。发布前做了以下处理：

  • 账户信息：裁剪掉 Windows 设置页中的账户名和邮箱；
  • QQ 会话：裁剪掉昵称、历史文件名和文件分享链接，只保留本次照片；
  • URL token：对 HTTP 请求中的 token 参数打码；
  • 链路层信息：对包详情中的 MAC 地址文本打码；
  • 网络地址：文中出现的 10.34.7.110、10.34.91.157 均为校园网内网地址，不是公网 IP；
  • 原始 pcap：不公开，避免其中包含的完整会话、文件内容和设备信息被二次利用。

另外，照片的 EXIF 中包含设备型号、拍摄时间等信息，这本身就是一种隐私泄露。日常发送照片前，建议在相册或系统中关闭“位置信息 / 拍摄参数”，或者使用工具清除 EXIF。

八、总结

问题 结论 主要证据
UDP 还是 TCP TCP（应用层 HTTP） 过滤后协议列全为 TCP；8082 → 63151；SYN, ACK；HTTP 记录
加密还是明文 明文 HTTP 请求 / 响应头可读；Server: QQ/1.0.0 (Tencent)；JPEG EXIF 字符串明文可见
文件恢复 可恢复 Content-Length: 2295406；JPEG 头 FF D8 FF；导出后得到约 2.19 MB 的照片

这次实验最大的体会是：“看起来像乱码”不等于加密。Wireshark 的十六进制视图里，JPEG、压缩包等二进制文件本来就是不可打印字节；判断是否加密，应该看协议结构、文件头、明文关键字和握手过程，而不是凭直觉。

另一个感受是：QQ 在局域网直连传输文件时，可能使用明文 HTTP。对普通用户来说，这意味着在不可信的 Wi-Fi 下，同一网络中的攻击者如果能够抓到流量，就可能直接还原你发送的照片和文件。因此，敏感文件应尽量在可信网络下传输，或者使用带端到端加密的工具；同时注意清理照片的 EXIF 信息。

本次实验的局限：

  • 只抓到了手机端 → PC 端的一次照片传输，PC-PC 端尚未单独抓包；
  • 结论与 QQ 版本、网络环境有关，换一个版本或换一个网络，端口和协议可能不同；
  • 没有对 TLS 流量做解密，因此如果遇到加密传输，只能做流量特征分析。

后续如果补做 PC-PC 端，我会用同样的方法对比两个场景的差异。

关于我对等保2.0的理解

一、等保2.0是什么

等保，全称“网络安全等级保护”，是我国网络安全领域的一项基础性制度。它的核心逻辑很朴素：根据信息系统被破坏后造成的危害程度，把系统分成不同等级，再对不同等级提出不同的安全要求，并配套备案、建设整改、测评和监督检查的流程。

我们现在说的“等保2.0”，指的是 2019 年发布、2019 年 12 月 1 日正式实施的新一代标准体系，主要文件包括：

  • GB/T 22239-2019《网络安全等级保护基本要求》
  • GB/T 22240-2020《网络安全等级保护定级指南》
  • GB/T 25070-2019《网络安全等级保护安全设计技术要求》
  • GB/T 28448-2019《网络安全等级保护测评要求》
  • GB/T 25058-2019《网络安全等级保护实施指南》

相比 1.0 时代，它最根本的变化是上位法变了：2017 年施行的《网络安全法》第二十一条明确要求“国家实行网络安全等级保护制度”，等保从此从部门规章上升为法律义务，不再只是“建议做”，而是“必须做”。

二、定级：五个等级

定级的依据是受侵害的客体和侵害程度两个维度，最终落到五个级别：

等级 名称 大致对应
第一级 自主保护级 一般系统，受损只影响公民、法人的合法权益
第二级 指导保护级 受损会严重损害公民、法人权益，或损害社会秩序和公共利益
第三级 监督保护级 受损会严重损害社会秩序和公共利益，或损害国家安全
第四级 强制保护级 受损会特别严重损害社会秩序和公共利益，或严重损害国家安全
第五级 专控保护级 受损会特别严重损害国家安全

实际工作中接触最多的是二级和三级。三级系统要求每年至少做一次等级测评，且二级以上系统在定级时一般需要经过专家评审。

三、控制项分类：技术 + 管理

等保2.0 的基本要求把所有控制项分成两大类：技术要求和管理要求，每一类下面再分层、分控制点、分控制项。这是理解等保最关键的框架。

（一）技术要求：一个中心、三重防护

技术要求被重构为五个层面，构成“一个中心、三重防护”的体系：

  1. 安全物理环境——机房选址、门禁、防火防水防雷、温湿度、电力供应、电磁防护等，管的是“房子”。
  2. 安全通信网络——网络架构、带宽与冗余、通信传输的完整性和保密性，强调传输过程不能被窃听篡改。
  3. 安全区域边界——边界防护、访问控制、入侵防范、恶意代码防范、安全审计，管的是“进出”。
  4. 安全计算环境——身份鉴别、访问控制、安全审计、入侵防范、数据完整性/保密性、数据备份恢复、剩余信息保护、个人信息保护，管的是“主机和应用”。
  5. 安全管理中心——系统管理、审计管理、安全管理、集中管控，把日志、账号、策略集中起来统一管理。

那个“一个中心”就是安全管理中心，三重防护指通信网络、区域边界、计算环境。这个设计的意图很清楚：安全不能靠单点堆设备，而要形成集中管控 + 分层纵深的闭环。

（二）管理要求：五个方面

管理要求同样分五个方面，覆盖系统的全生命周期：

  1. 安全管理制度——制度体系、发布流程、定期评审修订。
  2. 安全管理机构——岗位设置、人员配备、授权审批、沟通合作、审核检查。
  3. 安全管理人员——录用、离岗、安全意识培训、外部人员访问管理。
  4. 安全建设管理——定级备案、方案设计、产品采购、开发（自研/外包）、工程实施、测试验收、交付、等级测评、服务供应商管理。
  5. 安全运维管理——资产管理、介质管理、漏洞与风险管理、配置管理、密码管理、变更管理、备份恢复、安全事件处置、应急预案、外包运维等。

从渗透测试的角度看，管理要求里很多控制项其实正是攻击面：弱口令、默认账号、未及时打补丁、外包运维账号失控、日志缺失、应急响应形同虚设——这些在技术层面查不出来，却是实战中最常见的突破口。

四、和等保1.0的区别

我理解下来，1.0 到 2.0 的差异不只是“换了个版本号”，而是思路的升级。主要可以归纳为五点：

1. 名称与法律地位变了。
从“信息安全等级保护”改为“网络安全等级保护”，范围从“信息”扩大到整个网络空间；上位法从部门规章变成《网络安全法》，违规要承担法律责任。

2. 保护对象大幅扩展。
1.0 主要面向传统信息系统，2.0 把云计算、移动互联、物联网、工业控制系统、大数据全部纳入，采用“安全通用要求 + 安全扩展要求”的结构（即“1+N”）。这是最直观的变化：云上系统要额外满足云计算扩展要求，工控系统要满足工控扩展要求。

3. 技术架构重构了。
1.0 的技术要求是“物理安全、网络安全、主机安全、应用安全、数据安全及备份恢复”五类；2.0 重排为“物理环境、通信网络、区域边界、计算环境、管理中心”，并明确提出“一个中心、三重防护”。同时新增了可信验证、密码应用、个人信息保护等要求，从“防得住”走向“可验证”。

4. 管理要求更贴近实战。
2.0 把 1.0 的“系统建设管理/系统运维管理”调整为“安全建设管理/安全运维管理”，并强化了供应链安全，比如服务供应商管理、外包软件开发、外包运维管理——这对应的是近几年频发的供应链攻击。

5. 流程更闭环，要求更严。
定级、备案、建设整改、等级测评、监督检查形成完整闭环；二级以上定级需要专家评审；测评内容更细化、可操作性更强，不再是“有制度就行”，而是要有记录、有执行、能追溯。

一句话概括：1.0 解决的是“有没有”，2.0 解决的是“管不管用、能不能验证”。

五、从渗透测试视角看等保

作为渗透测试课程的学习者，我最大的体会是：等保和渗透测试是同一件事的两个视角。

  • 等保是合规视角，回答“该有的控制项有没有、配置对不对”，偏静态核查；
  • 渗透测试是攻击视角，回答“这些控制项在真实攻击下顶不顶得住”，偏动态验证。

两者并不冲突，而是互补。等保测评中也会用到渗透测试作为验证手段，比如验证边界防护是否真的能拦住未授权访问、身份鉴别是否存在弱口令、访问控制能否被越权绕过、数据传输是否真的加密。反过来说，等保给出的控制项清单，恰好是一份很好的渗透测试检查表：把每一条控制项翻译成“攻击者会怎么绕”，就能形成清晰的测试思路。

当然，做这件事的前提是授权。等保测评和渗透测试都必须有明确的授权范围和时间窗口，未经授权的测试本身就违反了等保和《网络安全法》的要求——这大概是这门课教给我最实用的一课。

六、小结

等保2.0 不是一个可以“买设备过关”的清单，而是一套以等级为基准、以业务为中心、覆盖技术与管理全生命周期的安全治理框架。它的技术框架可以记成“一个中心、三重防护”，管理框架可以记成“制度、机构、人员、建设、运维”五块；和 1.0 相比，核心变化在于对象扩展、架构重构、可信验证、供应链安全、法律强制。

对我个人来说，学等保最大的收获是建立了一种“从合规要求反推攻击面”的思维方式——这或许比记住多少条控制项更重要。
